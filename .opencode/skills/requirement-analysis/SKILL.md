# 需求分析

把原始需求转化为清晰、完整、与产品既有功能深度关联的落地需求。

## 前置条件

已加载 `product-knowledge` 技能并读取产品知识库（尤其 `relations.md`、`glossary.md`、`ui/pages.md`、`ui/design-system.md` 和相关功能文件）。

## 需求澄清（如有歧义）

当需求存在以下模糊点时，先向用户澄清，不臆测；在得到回答前暂停后续分析：
- 名词、缩写、页面名、单据名或状态名的含义不明确，或与已有术语存在多个对应关系
- 业务逻辑、状态流转、库存/金额影响、权限或异常处理存在多个合理解释
- 交互样式、入口位置、弹窗/抽屉形态、返回方式、手势或状态反馈无法确定
- 目标用户与使用场景不明确
- 需求边界/范围不清
- 优先级不确定
- 存在多个互相冲突的理解

用户回答后：

1. 将用户答案作为当前需求的最高优先级依据；
2. 回到原分析步骤继续执行，不重新发起相同问题；
3. 把已确认的名词、规则或交互结论写入 PRD 的依据/变更记录，并判断是否需要同步知识库。

## 拆解步骤

### 1. 背景与动机
明确 Why：这个需求的来源、要解决的业务/用户问题、业务价值。

### 2. 用户与场景拆分
识别涉及的用户角色、触发场景、使用频次。

### 3. 功能点拆解
将需求拆为独立、可交付的功能点。每个功能点包含：
- **描述**：做什么
- **业务规则**：如何做（明确、可判定）
- **边界与异常**：不做/异常时怎么办
- **优先级**：MoSCoW（Must/Should/Could/Won't）

### 4. 关联分析（核心）
对照 `relations.md` 与既有功能文件：
- **上游依赖**：本需求依赖哪些既有功能/数据
- **下游影响**：本需求会改变哪些既有功能的行为
- **复用可能**：是否可复用既有能力，避免重复建设
- **冲突检测**：是否与既有功能/规则/状态机冲突
- **术语一致**：检查是否引入新术语、新状态

### 4.5 页面影响分析（涉及界面时必须）
对照 `ui/pages.md` 与 `ui/design-system.md`：
- **落在哪些既有页面**：需求影响的页面ID（如 `sales-create`、`home`），引用页面快照。
- **复用页面范式**：沿用既有页面结构与交互范式（数据卡片/红色胶囊主按钮/分类聚合/左滑操作等），不自造布局。
- **新增页面**：若需新页面，说明其如何适配现有导航（顶部三Tab/更多功能页）与设计系统；结构缺失处标注「待补充」，不臆造。
- **风格一致性**：新元素不得与 `design-system.md` 冲突。

### 5. 数据与规则分析
- 核心数据实体与字段变化
- 业务状态流转（对齐 `glossary.md` 状态机）
- 对照 `data-dictionary.md` 标记字段、金额、数量、库存和状态的证据等级
- 对照 `metrics.md` 明确成功指标、公式、数据范围、基线和目标状态；目标未知时标记待确认
- 对照 `open-questions.md` 判断 P0/P1 问题是否会阻塞本期方案
- 权限与安全要求

### 6. 风险与依赖
- 技术风险、业务风险、外部依赖（第三方、合规）
- 对既有功能的影响风险
- 上线/回滚策略

### 7. 验收标准
为每个功能点定义 Given/When/Then 验收标准。

## 输出格式

```
## 需求分析：〈需求名〉
### 背景与目标
### 用户与场景
### 功能点拆解
| # | 功能点 | 优先级 | 说明 |
### 关联分析
| 关联功能 | 关系类型 | 影响 | 复用 |
### 页面影响分析
| 页面ID | 页面名 | 影响类型（改造/复用/新增） | 说明 |
### 数据与规则变更
### 风险与依赖
### 迭代规划
| 迭代 | 范围 |
### 验收标准
```

## 分析原则

1. **关联优先**：先找关联，再定方案；明确标注对既有功能的影响面。
2. **页面一致**：涉及界面时先读 `ui/pages.md` 与 `ui/design-system.md`，沿用既有页面范式，不自造布局。
3. **不臆测**：知识库缺失的信息，标注为假设或向用户确认。
4. **最小可行**：优先给出 MVP 范围，明确后续迭代。
5. **冲突显性**：与既有功能冲突时，指出冲突点并给出取舍建议。
