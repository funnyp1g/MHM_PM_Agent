## Context

当前项目为「卖货猫」服装零售进销存 App，无独立补货模块；补货需求已由 PRD（`docs/prd/2026-08-06-replenishment.md`）定义完整业务规则。产品已有货品管理（SKU/库存/价格）、进货入库、供应商管理、首页入口聚合、岗位权限等既有能力，可复用的公共组件包括：货品搜索/筛选、扫码能力、岗位权限、供应商选择器。动机详见 `proposal.md - Why`。

## Goals / Non-Goals

**Goals:**
- 复用既有货品搜索/筛选、扫码、岗位权限能力，避免重复建设。
- 补货单作为独立单据，MVP 阶段与库存、进货入库完全解耦（提交不改变库存、不生成入库单）。
- 数据模型上预留「供应商」「状态机」字段，便于迭代 2 与进货入库衔接。

**Non-Goals:**
- 不实现补货单转进货入库/入库联动（迭代 2）。
- 不做跨会话持久化补货车、缺货提醒、建议补货量、审批流。
- 不修改既有货品、进货、开单等模块的存量行为。

## Decisions

**D1：补货单采用独立单据模型，不直接落库存**
理由：补货是「采购请求」性质，真正到货需走进货入库；提交即入库会造成库存虚增与既有进货流程冲突。库存快照存于补货单明细，避免后续库存变动影响历史单据。
备选：提交即生成入库单/加库存 —— 与既有「进货入库」职责重叠，MVP 拒绝。

**D2：补货车状态存于客户端会话（内存）而非服务端**
理由：补货车是临时的选品聚合，MVP 无需跨会话；降低服务端状态管理成本。
备选：服务端持久化补货车 —— 需要补货车实体与清理策略，收益低，推迟到有明确需求再做。

**D3：补货单号规则 BHR + 日期 + 流水**
理由：与既有单据风格可读、可排序；正式实现前确认与进货单号规则是否统一。
备选：复用进货单号规则 —— 需确认编号段隔离，避免混号。

**D4：状态机「待补货 → 已补货/已作废」**
理由：MVP 中「已补货」由手动标记触发（迭代 2 改为入库动作联动），「已作废」仅待补货可操作，保证单据可追踪且不可误作废。
备选：无状态补货单 —— 无法追踪履约，不符合业务目标。

**D5：权限复用「进货」岗位权限**
理由：补货与进货同属采购域，复用既有权限模块（glossary 权限模块列表），避免新增权限项造成配置负担。
备选：新增「补货」独立权限项 —— 增加店主配置成本，与现有模块划分不一致。

## Risks / Trade-offs

- **补货单与进货入库衔接断裂**（补了不录）→ 提交成功页提供「去进货入库」引导；迭代 2 实现补货单一键转新建入库单并自动置「已补货」。
- **补货单性质理解偏差**（若业务预期提交即入库/加库存）→ 已在 PRD 显性标注为待确认假设（⚠️）；评审确认后若调整，涉及 spec 中「提交不改变库存」需求变更，需在 apply 前修订。
- **补货数量误操作/重复提交** → 数量上限 999 + 提交确认弹窗 + 提交中禁用按钮防重。
- **补货单号格式假设**（BHR+日期+流水）→ 与既有编号规则核对后确定，属实现细节，可在 apply 阶段落定，不影响 spec。

## Migration Plan

- 新增能力，无存量数据迁移。
- 上线：前端新增入口（首页进货卡片「补货」快捷按钮）与页面 + 服务端新增补货单数据模型与接口；与既有模块并行，无破坏性变更。
- 回滚：隐藏首页进货卡片「补货」按钮并下线补货接口即可，不影响既有单据与库存数据。
