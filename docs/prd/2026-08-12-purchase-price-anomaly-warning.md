## 二、背景与目标

### 2.1 背景

当前门店在新建进货单、扫码入库或通过其他方式添加货品时，需要在进货单明细中录入本次实际拿货价。拿货价一旦误填，进货单会改变库存成本相关数据，并进一步影响库存货值、销售数据中的预计利润以及经营分析中的毛利率。

现有 `purchase-create` 页面可以填写进货单基础信息并添加货品，但在用户修改拿货价时，没有将输入值与货品资料中已维护的原拿货价进行对比，也没有在录入当下提供风险提示。用户通常要到后续查看利润或库存数据时，才发现进价异常，纠正成本较晚。

### 2.2 目标

1. 还原当前版本进货单页面的主要结构和操作入口，保持现有进货流程连续可用。
2. 在进货单货品明细的拿货价输入框下方，实时提示本次输入值相对货品原拿货价的异常偏差。
3. 以货品资料中维护的拿货价作为对比基准，降低误填进价导致的库存货值、预计利润和毛利率异常。
4. 通过弱提示帮助用户核对，不改变本期既有入库提交流程，不因提示直接阻断正常的特殊价格采购。

### 2.3 非目标

- 不在本期新增价格审批、老板二次授权或强制拦截流程。
- 不在本期修改货品资料中的原拿货价。
- 不在本期新增历史进货价趋势、供应商价格分析或自动推荐拿货价。
- 不在本期改造 `purchase-list`、`purchase-detail` 的信息架构和已有单据操作。
- 不涉及 `replenishment-tab` 或 `08-replenishment` 的补货功能；两者与本需求无关。
- 不在本期调整利润、毛利率或库存货值的既有统计公式；本需求只在录入环节增加提醒。

## 三、用户与场景

| 用户角色 | 使用场景 | 用户诉求 |
|---------|---------|---------|
| 老板/门店经营者 | 新建进货单后手动修改某款货品的拿货价 | 输入时立即知道价格是否明显偏离原记录 |
| 老板/门店经营者 | 扫码入库后核对或修改拿货价 | 不需要离开进货单页面即可完成核价 |
| 老板/门店经营者 | 同一进货单添加多个货品 | 每个货品独立核对，避免一条异常价格影响整单判断 |

### 3.1 典型场景

**场景 A：误填过低价格**

- 货品资料原拿货价为 100 元。
- 用户在进货单中输入 79 元。
- 价格低于原拿货价 21%，输入框下方展示：`输入的拿货价低于原拿货价21%,请核对是否正常`。
- 用户可以修改价格，也可以保留该价格并继续进货；系统本期不强制阻断。

**场景 B：误填过高价格**

- 货品资料原拿货价为 100 元。
- 用户在进货单中输入 130 元。
- 价格高于原拿货价 30%，输入框下方展示：`输入的拿货价高于原拿货价30%,请核对是否正常`。

**场景 C：正常波动**

- 货品资料原拿货价为 100 元。
- 用户输入 85 元或 115 元，偏差未超过 20%。
- 输入框下方不展示异常提示，页面保持正常录入状态。

## 六、详细功能需求

### FP1 还原进货单页面结构

#### 功能描述

在不改变现有导航和业务入口的前提下，还原 `purchase-create` 页面当前可见结构，并在货品明细区域增加拿货价异常提示能力。

#### 页面结构要求

| 区域 | 还原内容 | 交互要求 |
|------|---------|---------|
| 顶部导航 | 返回按钮、标题「进货单」、右侧一键入库和单据工具入口 | 沿用当前页面位置、层级和返回方式 |
| 供应商区域 | 自动匹配供应商开关、供应商必填项 | 沿用当前控件和选择方式；不因本需求改变供应商规则 |
| 入库日期 | 入库日期选择项 | 沿用当前默认值和日期选择交互 |
| 备注 | 备注输入项 | 沿用当前输入能力和占位文案 |
| 添加货品区 | 扫码入库、选择货品、拍照入库 | 三种入口继续可用；通过任一入口添加的货品均进入本需求的价格校验范围 |
| 货品明细区 | 展示已添加货品及可编辑的本次拿货价 | 以货品为单位展示，拿货价输入框下方预留提示空间 |
| 底部固定操作区 | 合计金额、入库款数/件数、新增货品、确定 | 保持固定底部操作区；提示不得遮挡或挤压确定按钮 |

#### 业务规则

1. 页面入口、标题、供应商、入库日期、备注、货品添加方式和底部操作区沿用既有 `purchase-create` 页面。
2. 本期新增内容只位于已添加货品的拿货价输入区域下方，不新增页面、不新增顶部入口。
3. 用户通过扫码入库、选择货品或拍照入库添加货品后，只要该货品存在已维护的原拿货价，就进入偏差比较流程。
4. 页面还原中未被当前实机记录覆盖的货品明细排版，需沿用现有进货单组件和字段顺序，不得因为本需求自造新的页面布局。具体明细快照列为原型/开发实现待补充项。

#### 边界与异常

- 供应商、日期、备注和本次进货数量的既有必填、校验和提交规则不变。
- 货品明细为空时，不展示拿货价提示区域。
- 页面滚动时，底部固定操作区仍需保持可用，不能遮挡拿货价输入框和提示文本。
- 页面加载或添加货品失败时，沿用现有错误反馈；本需求不新定义网络错误页。

### FP2 货品明细展示和编辑本次拿货价

#### 功能描述

用户添加货品后，在对应货品明细中看到本次进货要使用的拿货价，并可在原有输入流程中编辑该值。系统同时保留货品资料中已维护的原拿货价作为对比基准。

#### 业务信息

| 信息 | 含义 | 用户是否可编辑 |
|------|------|----------------|
| 货品名称/款号 | 当前添加的货品识别信息 | 沿用既有页面规则 |
| 颜色/尺码/SKU | 当前进货明细的规格信息 | 沿用既有页面规则 |
| 入库数量 | 本次入库数量 | 沿用既有页面规则 |
| 原拿货价 | 货品资料中已维护的拿货价，用于对比 | 否；仅作为参照数据 |
| 本次拿货价 | 本次进货单使用的拿货价 | 是；沿用当前进货单编辑能力 |
| 价格偏差提示 | 本次拿货价相对原拿货价的差异提示 | 系统计算，不可编辑 |

#### 业务规则

1. 对比基准为当前货品资料内维护的「拿货价」，简称「原拿货价」。
2. 本次拿货价为用户在进货单货品明细中实际输入或修改的价格。
3. 价格校验按单条货品明细执行；同一进货单中不同货品、不同 SKU 分别计算，不使用整单平均价。
4. 本次拿货价输入为空、格式不合法或未完成输入时，不计算偏差，不显示低于/高于提示。
5. 用户修正本次拿货价后，提示需依据最新输入值重新计算，不保留旧提示。
6. 本期提示只用于风险提醒，不改变本次拿货价的实际保存值；用户可以继续编辑，也可以按现有流程点击「确定」。

#### 边界与异常

- 原拿货价不存在、为空或无法作为有效正数比较时，不展示偏差提示；本期不阻止用户录入本次拿货价。
- 原拿货价为 0 时，不进行百分比比较，避免除以 0；本期不显示异常提示。
- 本次拿货价为 0 或负数时，沿用既有价格输入校验；本需求不替代原有金额合法性校验。
- 同一货品重复添加时，每个明细行按当前明细的本次拿货价独立计算；不以其他行的输入值覆盖本行提示。
- 货品资料原拿货价在页面打开后被其他操作修改时，本期以当前明细加载时取得的原拿货价作为本次提示的参照，避免同一页面内提示基准随意变化；该规则需在评审时确认。

### FP3 拿货价偏差实时提示

#### 触发条件

以原拿货价为基准，计算本次拿货价相对原拿货价的百分比偏差：

`偏差百分比 = (本次拿货价 - 原拿货价) / 原拿货价 × 100%`

当满足以下任一条件时显示提示：

- 本次拿货价 < 原拿货价 × 80%：显示低于提示。
- 本次拿货价 > 原拿货价 × 120%：显示高于提示。

本 PRD 按用户原始表述将「低于/高于 20%」解释为严格超过 20% 的偏差；正好低于 20% 或高于 20% 的边界值不显示提示。若业务希望边界值也触发，需要在评审时改为「达到或超过 20%」。

#### 提示文案

低于时：

`输入的拿货价低于原拿货价{偏差百分比}%,请核对是否正常`

高于时：

`输入的拿货价高于原拿货价{偏差百分比}%,请核对是否正常`

其中：

- `{偏差百分比}`取绝对偏差值，不展示正负号。
- 默认展示为百分比数值，建议保留 1 位小数，末尾为 0 时去掉；例如 21%、20.5%。最终精度需在 UI 评审时确认。
- 文案为输入框下方的小字辅助提示，不使用弹窗，不显示全局 Toast，不改变页面跳转。

#### 状态表现

| 状态 | 输入框下方表现 | 价格是否可继续编辑 | 「确定」是否可点击 |
|------|----------------|-------------------|-------------------|
| 未添加货品 | 不展示提示 | 不适用 | 沿用既有规则 |
| 原拿货价缺失/为 0 | 不展示提示 | 是 | 沿用既有规则 |
| 输入为空/不合法 | 不展示本需求提示 | 沿用既有价格校验 | 沿用既有规则 |
| 偏差未超过 20% | 不展示提示 | 是 | 是，沿用既有规则 |
| 低于原拿货价超过 20% | 输入框下方展示低于提示 | 是 | 是，不因本提示禁用 |
| 高于原拿货价超过 20% | 输入框下方展示高于提示 | 是 | 是，不因本提示禁用 |
| 用户修改回正常范围 | 提示即时清除 | 是 | 是，沿用既有规则 |

#### 交互要求

1. 提示与拿货价输入框保持垂直关联，显示在对应输入框正下方。
2. 提示使用小字号和警示色，但不能使用错误态样式暗示输入一定非法；建议沿用设计系统 `--color-warning`，并同时保留完整文字说明。
3. 提示出现后不得导致货品明细布局跳动到无法操作；页面需预留一行提示高度，或使用稳定的行内布局。
4. 多条货品同时异常时，每条货品只在自己的输入框下方展示提示，不在页面顶部汇总成一个笼统警告。
5. 用户清空输入、重新输入、删除货品或离开当前编辑状态时，提示跟随对应明细状态即时更新。
6. 提示不需要用户点击关闭；当输入恢复到正常范围或明细被删除时自动消失。

#### 示例

| 原拿货价 | 本次拿货价 | 偏差 | 是否提示 | 预期文案 |
|---------|-----------|------|---------|---------|
| 100 | 79 | 低于 21% | 是 | 输入的拿货价低于原拿货价21%,请核对是否正常 |
| 100 | 80 | 低于 20% | 否 | - |
| 100 | 85 | 低于 15% | 否 | - |
| 100 | 120 | 高于 20% | 否 | - |
| 100 | 121 | 高于 21% | 是 | 输入的拿货价高于原拿货价21%,请核对是否正常 |
| 100 | 130 | 高于 30% | 是 | 输入的拿货价高于原拿货价30%,请核对是否正常 |

### FP4 多货品独立校验

#### 业务规则

1. 每个货品明细单独保存原拿货价、本次拿货价和提示状态。
2. 某一行出现异常提示，不影响其他行的输入、数量编辑和删除。
3. 某一行恢复正常后，只清除该行提示，不清除其他异常行提示。
4. 货品明细排序、合计金额和入库款数/件数的现有规则不变。
5. 提示本身不计入货品数量、不计入金额、不改变库存，不产生单独单据记录。

### FP5 与既有提交流程兼容

#### 业务规则

1. 异常提示为软提醒，不阻止用户点击「确定」。
2. 用户点击「确定」时，沿用现有进货单的供应商、日期、货品、数量、金额和提交校验。
3. 本期不新增确认弹窗，不要求用户逐条点击「已核对」。
4. 如果既有价格输入规则认为当前值为空、负数或格式错误，仍按原有错误校验处理；本需求提示不能覆盖或降低原有校验级别。
5. 入库成功后，后续库存、库存货值、销售数据、预计利润和毛利率继续使用既有进货成本口径；本需求不修改历史单据，也不自动更正数据。
6. 进货单被取消、返回或作废时，提示状态随当前页面或明细状态结束，不新增额外状态。

## 七、用户流程

### 7.1 正常流程

```text
首页 -> 进货 -> 选择入库方式/进货单 -> 添加货品
  -> 展示货品明细和本次拿货价
  -> 用户输入或修改本次拿货价
  -> 系统与货品原拿货价比较
  -> 偏差未超过20%：不显示提示
  -> 偏差超过20%：输入框下方显示提示
  -> 用户核对并可继续修改
  -> 点击确定 -> 沿用既有进货入库流程
```

### 7.2 异常提示流程

```text
添加货品
  -> 原拿货价有效
  -> 输入本次拿货价
  -> 计算相对偏差
  -> 低于原拿货价超过20% / 高于原拿货价超过20%
  -> 展示对应方向的小字提示
  -> 用户修改价格
  -> 重新计算
  -> 正常范围：自动清除提示
  -> 仍异常：更新偏差百分比和方向文案
```

### 7.3 状态流转

```text
未校验
  -> 输入为空/无有效原拿货价：不显示提示
  -> 输入有效且偏差未超过20%：正常
  -> 输入有效且低于原拿货价超过20%：低价提示
  -> 输入有效且高于原拿货价超过20%：高价提示
低价提示/高价提示
  -> 修改输入：重新计算
  -> 回到正常范围：正常
  -> 删除明细：结束
```

## 九、业务信息与效果衡量

### 9.1 用户需要看到和确认的信息

用户在进货单中需要看到：

1. 当前货品识别信息，包括货品名称、款号及 SKU/颜色/尺码等既有明细信息。
2. 货品资料中维护的原拿货价，作为核价参照；是否直接展示原拿货价需在 UI 评审确认，至少必须可供系统计算。
3. 本次进货要使用的拿货价输入框。
4. 价格偏离方向和偏离百分比。
5. 「请核对是否正常」的明确提醒。
6. 继续编辑和提交的入口，避免提示变成无解释的阻断。

### 9.2 影响的数据口径

| 数据对象/指标 | 本需求影响 |
|--------------|------------|
| 货品款的拿货价 | 作为对比基准读取，不在本期修改 |
| 进货单/入库单的本次拿货价 | 继续由用户输入并沿用既有保存规则 |
| 库存 | 继续由既有入库动作改变，本期提示本身不改变库存 |
| 库存货值 | 继续使用既有 SKU/进货价口径，本期不修改计算公式 |
| 预计利润 | 继续使用既有销售数据口径，本期不修改计算公式 |
| 毛利率 | 继续使用既有销售单和进货成本口径，本期不修改计算公式 |

### 9.3 成功标准

- 指标名称：拿货价异常提示覆盖率。
- 业务目的：确认系统能在用户输入明显偏离原拿货价时及时展示提示。
- 计算建议：触发异常阈值的有效价格输入中，成功展示对应方向提示的明细数 / 触发异常阈值的有效价格输入明细总数。
- 数据范围：`purchase-create` 页面内通过扫码入库、选择货品、拍照入库添加的货品明细；按当前门店统计。
- 观察周期：上线后首个完整经营周期，具体周期和负责人待业务确认。
- 目标值：待业务确认。
- 辅助观察指标：因误填进价导致的后续价格更正次数、进货单编辑次数、库存货值/预计利润异常反馈次数；具体埋点和统计口径待技术与业务共同确认。

1. 本期目标角色沿用项目默认范围：老板账号；不扩展店长/店员权限矩阵。

5. 如果后续增加强制拦截、审批或异常价格操作日志，需要另行提出需求，不纳入本期默认行为。

## 十三、风险与依赖

### 13.1 业务风险

- 服装采购存在真实价格波动、批量价、临时优惠和换供应商等情况，单一 20% 阈值可能产生误报，因此本期采用提示而非阻断。
- 货品原拿货价可能未维护、为 0 或长期未更新，无法作为可靠对比基准；此类情况本期不提示，并需要后续补充数据维护规范。
- 若用户忽略提示仍继续入库，错误进价仍可能进入后续库存和经营分析；本期目标是降低误填概率，不承诺完全消除异常数据。

### 13.2 页面与实现依赖

- 依赖货品资料能够提供当前货品的有效原拿货价。
- 依赖所有进入 `purchase-create` 货品明细的添加方式统一经过拿货价字段校验。
- 依赖移动端输入框可在窄屏上稳定展示提示文本，并不遮挡底部固定操作区。
- 依赖既有进货单价格合法性校验继续生效。
- 完整页面还原和交互验收依赖用户对 Open Design 原型的业务评审，以及对添加货品后的真实明细布局进行补充观察。

### 13.3 回滚策略

若提示造成明显误报或影响录入，可关闭本期偏差提示开关/回滚提示逻辑；既有进货单页面、货品添加和入库提交流程保持不变。具体开关和发布方式属于技术实现待确认，不在正文展开。

## 十四、假设与待确认项

| 优先级 | 事项 | 本 PRD 暂定口径 | 影响 |
|-------|------|----------------|------|
| P1 | 20%边界是否包含等于 | 按用户原文解释为严格超过 20% 才提示；80% 和 120% 边界不提示 | 影响阈值判断和验收用例 |
| P1 | 百分比展示精度 | 建议保留 1 位小数，整数去掉小数；例如 21%、20.5% | 影响提示文案展示 |
| P1 | 原拿货价是否直接展示给用户 | 系统必须读取并用于比较；是否在页面额外展示原拿货价，待 UI 评审确认 | 影响用户核价效率和明细布局 |
| P1 | 原拿货价读取时点 | 暂按货品添加到当前进货单时取得的货品维护拿货价作为本次参照 | 影响页面停留期间货品价格被修改时的提示一致性 |
| P2 | 加载/失败状态的具体视觉细节 | 已在 Open Design 原型中覆盖，待用户评审确认 | 影响页面还原验收 |
| P2 | 效果指标基线与目标值 | 口径已定义，基线、目标值、观察周期和负责人待业务确认 | 影响上线效果评估 |

> 以上待确认项不改变本期核心方案：在 `purchase-create` 的每条货品拿货价输入框下方，针对相对货品原拿货价偏差超过 20% 的情况展示低于/高于提示，并保持可继续编辑和提交。

## 十五、验收标准

### AC1 页面结构还原

- **Given** 用户从首页进货入口进入新建进货单页面
- **When** 页面加载完成且尚未添加货品
- **Then** 页面展示返回按钮、标题「进货单」、右侧现有操作入口、自动匹配供应商、供应商、入库日期、备注、三种添加货品方式以及底部合计/新增货品/确定区域，且整体布局遵循当前实机页面

### AC2 添加货品后展示拿货价输入

- **Given** 用户在 `purchase-create` 中通过扫码入库、选择货品或拍照入库添加一个有效货品
- **When** 货品明细加载完成
- **Then** 对应明细展示本次拿货价输入框，并保留当前货品的原拿货价用于比较；输入框下方存在稳定的提示展示位置

### AC3 低于阈值时提示

- **Given** 货品原拿货价为 100 元
- **When** 用户输入本次拿货价 79 元
- **Then** 输入框下方显示「输入的拿货价低于原拿货价21%,请核对是否正常」或按约定精度格式化后的等价文案

### AC4 高于阈值时提示

- **Given** 货品原拿货价为 100 元
- **When** 用户输入本次拿货价 121 元
- **Then** 输入框下方显示「输入的拿货价高于原拿货价21%,请核对是否正常」或按约定精度格式化后的等价文案

### AC5 正常范围不提示

- **Given** 货品原拿货价为 100 元
- **When** 用户输入 85 元、100 元或 115 元
- **Then** 输入框下方不显示本需求新增的低于/高于提示

### AC6 20%边界按暂定规则处理

- **Given** 货品原拿货价为 100 元
- **When** 用户输入 80 元或 120 元
- **Then** 按本 PRD 暂定的严格超过 20%规则，不显示本需求新增提示

### AC7 修改后实时更新

- **Given** 当前拿货价输入为 79 元，页面已显示低于提示
- **When** 用户将拿货价修改为 100 元或 115 元
- **Then** 低于提示立即消失，且不残留旧的偏差百分比

### AC8 方向和百分比更新

- **Given** 当前拿货价输入为 79 元，页面已显示低于 21%提示
- **When** 用户将拿货价修改为 130 元
- **Then** 原低于提示被替换为高于 30%提示，不同时显示两条方向相反的提示

### AC9 多货品独立提示

- **Given** 一个进货单中有货品 A 和货品 B，货品 A 偏低超过 20%，货品 B 偏高超过 20%
- **When** 两条明细同时展示
- **Then** A 在自己的拿货价输入框下显示低于提示，B 在自己的输入框下显示高于提示，互不覆盖

### AC10 缺少原拿货价时不误报

- **Given** 货品原拿货价为空、无效或为 0
- **When** 用户输入本次拿货价
- **Then** 不显示本需求新增的偏差提示，且不因本需求阻止用户继续沿用既有进货流程

### AC11 输入非法时沿用原校验

- **Given** 用户输入空值、负数或不符合既有金额格式的本次拿货价
- **When** 页面执行现有输入校验
- **Then** 沿用既有价格输入错误反馈；不得将本需求的偏差提示当作合法性校验，也不得用偏差提示覆盖原错误信息

### AC12 异常提示不阻断提交

- **Given** 某条货品明细显示低于或高于 20% 的偏差提示，且其他必填项和既有校验均通过
- **When** 用户点击底部「确定」
- **Then** 「确定」仍可点击，进货单沿用既有提交流程，不要求额外确认本提示，不因本需求增加拦截

### AC13 金额和库存口径不变

- **Given** 用户输入一个触发提示的本次拿货价并完成既有入库流程
- **When** 进货单保存或入库成功
- **Then** 本次拿货价按用户最终输入值沿用既有保存规则，提示本身不额外改变入库数量、应付/实付金额、库存、库存货值、预计利润或毛利率计算方式

### AC14 提示不遮挡底部操作

- **Given** 页面存在一条或多条异常价格提示
- **When** 用户滚动查看货品明细并准备点击底部操作
- **Then** 提示文本完整可读，货品输入框可编辑，底部「新增货品」和「确定」不被提示遮挡，页面符合移动端安全区域要求

### AC15 三种添加方式一致

- **Given** 用户分别通过扫码入库、选择货品和拍照入库添加存在有效原拿货价的货品
- **When** 货品进入进货单明细并输入偏离超过 20% 的本次拿货价
- **Then** 三种方式添加的货品均展示相同判断规则、方向文案和提示位置
